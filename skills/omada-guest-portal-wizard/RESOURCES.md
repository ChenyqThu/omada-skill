# Resources — guest-portal-wizard

## `PortalSetting` VO — the interesting fields

The `omada_portal_wizard` tool passes `portalSetting` verbatim to
`addPortal`. Typical fields (names are indicative — always consult
the current Omada OpenAPI spec):

| Field              | Type      | Notes                                                                       |
| ------------------ | --------- | --------------------------------------------------------------------------- |
| `name`             | string    | Human-readable portal name. Shows in the controller UI.                     |
| `authType`         | enum      | `None` / `Voucher` / `Local` / `Radius` / `Facebook` / `External` (varies). |
| `ssidIds`          | string[]  | Site-scoped SSID IDs this portal applies to.                                |
| `landingUrlEnable` | bool      | Redirect after login?                                                       |
| `landingUrl`       | string    | URL to redirect to when `landingUrlEnable` is true.                         |
| `sessionTimeout`   | int (min) | Per-session lifetime. Omit to take Omada's default (varies by `authType`).  |
| `rateLimit`        | object    | `{ upLimit, downLimit, upLimitUnit, downLimitUnit }`. Optional.             |
| `logoUrl`          | string    | Branding — HTTPS URL reachable from the guest network.                      |
| `backgroundImgUrl` | string    | Branding.                                                                   |
| `primaryColor`     | string    | `#RRGGBB`.                                                                  |
| `termsOfService`   | string    | Plain text or URL per spec; long-form content is rejected in some versions. |
| `voucherPool`      | object    | Voucher-auth specific. Pre-existing pool ID + duration.                     |
| `radiusProfile`    | object    | Radius-auth specific.                                                       |

## `authType` quick reference

- `None` — click-through only, no credentials. Fastest to stand up;
  legally thin if you need consent.
- `Voucher` — codes generated by the operator; pair with
  `voucherPool`. Common for hotels and conference venues.
- `Local` — controller-hosted usernames. Good for small-office staff
  guest Wi-Fi.
- `Radius` — delegates to an external Radius. Needs
  `radiusProfile.serverIp` + shared secret pre-configured.
- `Facebook` — OAuth bounce. Rarely used post-2024 because consent +
  privacy posture got harder.
- `External` — send guests to a third-party SAML/OAuth portal.
  Requires URL + secret pre-configured on the controller.

## SSID discovery

`omada_portal_wizard` needs SSID IDs, not SSID names. M3 does not ship
a dedicated SSID-list tool; use either:

1. The controller UI → Settings → Wireless Networks for the IDs, OR
2. `omada_script { operationId: "listSsids" }` (or whichever
   operationId the current spec uses) through the escape hatch.

Record the mapping in the operator's runbook, not in this skill.

## Minimal `PortalSetting` example (voucher auth)

```jsonc
{
  "name": "guest-lounge",
  "authType": "Voucher",
  "ssidIds": ["ssid-site042-guest"],
  "sessionTimeout": 120,
  "logoUrl": "https://cdn.acme.com/logos/acme.svg",
  "primaryColor": "#0f5cff",
  "termsOfService": "https://cdn.acme.com/legal/wifi-tos.txt",
  "voucherPool": {
    "poolId": "vp-weekly",
    "durationMinutes": 120,
  },
}
```

Anything beyond that (branding, captive-portal-detection URLs, MAC
bypass allowlist) is site-specific — don't invent defaults.

## Site-template interop

If the site-template bundles the SSID + portal-id binding:

- Bind the template first via `omada_apply_site_template`.
- Then run the portal wizard so the SSID already references "some
  portal with id X" on the controller.

If the site-template has _not_ been bound yet and you create the
portal first, the SSID's `portalId` pointer stays at its previous
value until the template is applied. Operators commonly misread this
as "the portal isn't wired up" when the SSID is simply still looking
at the old portal.
